Four kinds of arrays

Lesson 0

Chapter 1 ran a small open model, LiquidAI's LFM2.5-230M, on a laptop CPU, and printed three shapes on the way: (1, 6), (1, 6, 1024), and (1, 6, 65536). This chapter explains what each number in those shapes means. Then it sorts every array a running model touches into one of four kinds, because the kinds behave very differently.

Everything numeric inside a model is an array of numbers with a shape. Such an array is called a tensorTerm tensorAn array of numbers with a shape. Each position in the shape is an axis.. The shapeTerm shapeThe list of axis sizes, in order. (2, 6, 1024) has three axes. is the list of its sizes, in order. Each position in the shape is an axisTerm axisOne direction you can index along, like batch, position, or width. Name it before you use it., one direction you can index along. (1, 6, 1024) has three axes, of sizes 1, 6, and 1,024.

Here are the four kinds of arrays:

  • ParametersTerm parametersThe model's learned numbers, also called weights. Training sets them. Running the model only reads them. are the model's learned numbers. They are loaded once and only read.
  • ActivationsTerm activationAn array the model computes during one call, like a block's output. Made fresh each call, then dropped. are arrays the model computes during one call. They are made fresh each call, then dropped.
  • The cache is what the model keeps between steps of one reply, so it does not redo earlier work. It belongs to one conversation.
  • The config is a small file of numbers, like the width and the number of blocks. It is not an array, but it fixes every array's shape.

Mixing up the kinds causes real bugs: a slice that answers the wrong question, a parameter count that is too big, and an answer about the wrong country. We run each case on the same model as chapter 1, with the real output.

What you will be able to do#

  1. Name every axis of a real shape, pick the slice you mean, and spot the wrong-axis bug from its shape.
  2. Read a parameter's name and shape: which block, which part, how many numbers go in and come out, and which config values set that shape.
  3. Count the parameters once, even when a shared array appears under two names.
  4. Tell parameters from activations, and show that running a model never changes its parameters.
  5. Explain what the cache keeps between steps, how it grows, and why it belongs to exactly one conversation.
  6. Sort any array in a running model by kind and lifetime, and name the chapter that covers each part in depth.

Array Shape Axes, in order
token IDs (2, 6) batch, position
embeddings (2, 6, 1024) batch, position, width

The first axis is the batchTerm batchSeveral independent prompts stacked into one array, so one call handles them all.: several independent prompts stacked into one array, so one call handles them all. Here it has two entries, France and Spain. The second axis is the positionTerm positionWhere a token sits in the sequence: 0 for the first token, 1 for the next., where a token sits in the sequence. Both prompts are six tokens long, so it has six entries. The embeddings add a third axis, the widthTerm widthHow many numbers describe one token inside the model: 1,024 here.: how many numbers describe one token inside the model. That is 1,024 here. The logits replace the width with the vocabulary: one score for each of the 65,536 possible next tokens.

The two prompts do not affect each other. Prompt 0 gets Paris at 95.22 percent, exactly as it did alone in chapter 1. Prompt 1 gets Madrid at 93.66 percent. Batching is a way to do two calls at once, not a way to mix them.

To get one prompt's next token, the script indexes out.logits[b, -1]. That means batch entry b, last position, every vocabulary entry. An axis you give an index to drops out. An axis you leave out keeps all its entries. The result has one axis left, of size 65,536, and argmax picks the highest score on it.

Check

Show the answer

Only the first axis changed, from 1 to 2. The position axis is still 6, and the vocabulary axis is still 65,536.

The wrong axis

Lesson 2

Indexing code runs as long as the indexes fit the shape. It does not check that you meant the right axis. Here are two ways to ask for "the last one":

logits[:, -1] keeps every batch entry and takes the last position. That gives one next token per prompt: Paris and Madrid. logits[-1] indexes the first axis instead. It takes the last batch entry, the Spain prompt, and keeps all six positions. That gives six predictions, one after each position of the Spain prompt.

Both lines run without an error, and both print real tokens. The wrong one even looks plausible. Its fourth entry is the model's guess after The capital of, and the guess is France, at 19 percent. A bug like this can slip through a quick glance at the output.

The shape catches it. You wanted one row per prompt, so the first size should be 2. It is 6. When you index an array, write down the shape you expect, then compare it to the shape you got.

Check

A function expects (batch, vocabulary) and receives (6, 65536) from a batch of two prompts. What went wrong?

Show the answer

The code indexed the batch axis where it meant the position axis. It got every position of one prompt instead of the last position of every prompt.

Read a weight's name

Lesson 3

Chapter 1 counted 229,693,184 parameters. They live in named arrays. The script below lists them all, then prints the names and shapes for everything outside the blocks, plus one conv block and one attention block:

The model's 229,693,184 numbers sit in 132 arrays. A name reads like a path, from the outside in. Take layers.2.self_attn.q_proj.weight:

  • layers.2 is block 2, the third block. The code calls the blocks layers.
  • self_attn is that block's mixer, an attention mixer.
  • q_proj is one part of the mixer, the query projection. Chapter 8 explains what it does.
  • weight is the array of learned numbers that part uses.

The word "layer" means different things in different places. In this code, layers.2 is a whole blockTerm blockOne repeated stage that reworks every token's numbers. This model stacks 14 of them. The code calls them layers., the repeated stage from chapter 1. Each block holds 8 or 11 arrays. People also call a single matrix inside a block a layer. So when someone says "layer," read the name to see which they mean.

The names show the two kinds of block. Block 0 is a conv block. Its mixer has a conv filter and two projections. Block 2 is an attention block. Its mixer has query, key, value, and output projections, plus two small norms. Both have the same feed-forward part, w1, w3, and w2, and the same two norms. All eight conv blocks hold the same eight array names, and all six attention blocks hold the same eleven. One name misleads. embedding_norm.weight is the final norm: the model applies it after the last block, not after the embeddings. A name is a strong hint, and the model code is the check. With the embedding table and the final norm, that makes 1 + 8 × 8 + 6 × 11 + 1 = 132 arrays.

Most of these arrays have two axes. An array with two axes is a weight matrixTerm weight matrixA parameter with two axes, stored as (numbers out, numbers in)., and this code stores it as (numbers out, numbers in). w1 has shape (2560, 1024), so it takes a token's 1,024 numbers and produces 2,560. w2 has shape (1024, 2560), so it brings them back to 1,024. That is the widening and narrowing of the feed-forward part from chapter 1. The embedding table also has two axes, but the model reads it as a lookup: each token ID selects one row. The norms are single lists of 1,024 numbers, one scale per number in a token's vector. Chapter 3 shows what multiplying by a weight matrix computes.

Check

What does layers.4.self_attn.k_proj.weight hold, and what is its shape?

Show the answer

It is the key projection in block 4's attention mixer. Every attention block has the same arrays, so its shape is (512, 1024), like block 2's.

The config sets every shape

Lesson 4

The shapes are not arbitrary. A few numbers in the model's configTerm configThe small file of numbers, like the width and the number of blocks, that fixes every array's shape. file, config.json, fix all of them:

Match each number to the shapes in names.py:

Config value Shapes it sets
vocab_size 65,536 and hidden_size 1,024 the embedding table (65536, 1024)
hidden_size 1,024 the width of every block's input and output, every norm, out_proj (1024, 1024)
intermediate_size 2,560 w1 and w3 (2560, 1024), w2 (1024, 2560)
num_attention_heads 16 q_proj (1024, 1024): 16 heads of 64 numbers each, and 16 × 64 = 1,024
num_key_value_heads 8 k_proj and v_proj (512, 1024): 8 groups of 64, and 8 × 64 = 512
conv_L_cache 3 the conv filter (1024, 1, 3): one filter 3 positions wide for each of the 1,024 numbers
num_hidden_layers 14 14 blocks, layers.0 to layers.13

The width of 64 per head is hidden_size divided by num_attention_heads. The conv block's in_proj makes three 1,024-wide parts at once, which gives 3,072. The code calls them B, C, and x. x holds the numbers the filter mixes, and B and C scale them on the way in and on the way out. The conv filter's middle 1 means each of the 1,024 filters reads only its own number. Chapter 10 opens the conv block.

The config is not learned, and it holds no arrays. The loading code reads the config, builds empty arrays of those shapes, and then fills them from the weights file. The learned values fit only the shapes they were trained in. We set intermediate_size to 3,072 and loaded the same weights, and loading stopped with a size-mismatch error, because the stored arrays no longer fit.

Check

Which config value would you change to make the feed-forward part wider, and which three arrays would change shape? intermediate_size. It sets the shapes of w1, w3, and w2. A wider model also needs new learned values, because the old ones do not fit.

2.5Counting the parameters once#

You are hereOne table, two names

Code that saves or loads models works with the model's state_dict(), a mapping from each name to its array. Counting the numbers in it seems like a good way to count parameters. It gives the wrong answer:

The state dict counts 67,108,864 more numbers, exactly one embedding table of 65,536 × 1,024. Chapter 1 showed why. The output layer reuses the embedding table instead of holding its own. The state dict lists that one array under two names, model.embed_tokens.weight and lm_head.weight, and summing it counts the table twice. model.parameters() gives each shared array once.

Equal values would not prove the two names are one array. Two separate copies could hold the same numbers. The last line checks the address in memory where each array's numbers start. Both names point to the same address, so they are the same array.

Check

A tool reports 296.8 million parameters for this model. What would you check first?

Show the answer

Whether it summed every name in a saved listing. The extra 67.1 million is the embedding table counted a second time, under the output layer's name.

Made for one call

Lesson 5

The parameters are what the model holds. Everything it computes from them during a call is an activation: the embeddings, every block's output, the 2,560-wide numbers inside each feed-forward part, the logits. The script below hooks every layer that holds weights and adds up the numbers each one hands on. It runs a 6-token prompt and a 352-token prompt:

The parameters did not change with the prompt. The activations grew in step with it: 242,688 numbers per position, both times. Every activation has a position axis, so a longer prompt makes every one of them longer, and a bigger batch multiplies them again. This count covers only what the weight-holding layers hand on. It leaves out arrays made inside a single operation, such as attention's scores, which grow with the square of the prompt length. The output layer alone hands on 65,536 numbers per position, more than a quarter of the total, because it scores every vocabulary entry.

These are numbers handed from one layer to the next, not memory in use at one moment. Most activations are released as soon as the next layer has read them. Chapter 13 measures what a model actually needs in memory.

Running the model reads the parameters and never writes them. The next script copies all 132 arrays, generates three slogans, and compares:

Every number is exactly as it was. A model does not learn from the prompts you send it. Training changes parameters, and chapter 6 shows how. Running a model only makes activations, and sometimes a cache.

Check

Does a 352-token prompt use more parameters than a 6-token prompt?

Show the answer

No. Both calls read the same 229,693,184 parameters. The 352-token prompt makes about 59 times more activations.

The cache

Lesson 6

Chapter 1's loop sent the whole sequence through the model at every step. Step 0 processed 21 positions, step 1 processed 22, and so on, recomputing the same early positions again and again. The cacheTerm cacheWhat the model keeps between steps of one reply, so earlier tokens are not recomputed. It belongs to one conversation. avoids that. After each call, the model keeps what later steps need, and the next call sends only the new token.

The reply is the same eight tokens as chapter 1's loop, The capital of France is Paris. and the end-of-turn token. The difference is the input column. The first call sends the 21-token prompt. Every later call sends one token.

The two kinds of block keep different things:

  • Each attention block keeps the keys and valuesTerm keys and valuesThe arrays attention looks back at. The cache keeps them for every earlier position., the arrays attention looks back at, for every position so far. Name the axes of (1, 8, 21, 64): batch, 8 key-value groups, 21 positions, 64 numbers per group. The position axis grows by one each step, to 28 by the end. The cache grows with the conversation.
  • Each conv block keeps its conv stateTerm conv stateWhat a conv block keeps between steps: the last three positions of the numbers its filter reads.: the last three positions of the numbers its filter reads. Name the axes of (1, 1024, 3): batch, 1,024 numbers, 3 positions. Here the position axis comes last, and it never grows. Each step drops the oldest position and adds the newest.

That second point is the reason to name axes instead of assuming them. In the keys, the positions come before the 64 numbers of each group. In the conv state, the 1,024 numbers come first and the 3 positions last. Same idea, different order.

The cache is stateTerm stateData the model carries from one call to the next, like the cache.: data the model carries from one call to the next. It is not parameters. It starts empty, it is built from activations, and it changes every step. It also saves real work. We ran both loops for 64 steps from this prompt without stopping at the end token. The cached loop processed 84 positions, the recompute loop processed 3,360, and both produced the same 64 tokens. How much time that saves depends on the runtime and the hardware. Chapter 9 covers the loop with its cache, and chapter 13 covers the cost.

The cache grows with every token. Each attention block keeps 2 × 8 × 64 = 1,024 numbers per position, so the six attention blocks keep 6,144 numbers per position. The eight conv blocks keep 24,576 numbers in total, however long the conversation runs. We calculated that at 10,000 positions, the cache would hold about 61 million numbers, about a quarter as many as the parameters.

Check

After 28 positions, the keys in block 2 have shape (1, 8, 28, 64). What shape will they have after 100 positions, and what about the conv state?

Show the answer

The keys will be (1, 8, 100, 64). The conv state stays (1, 1024, 3).

The wrong cache

Lesson 7

The cache stands in for every earlier position. The model never sees those tokens again, only what the cache kept from them. So the cache must come from the same conversation as the new token. Here is what happens when it does not:

The two prompts are both six tokens long, and they differ only at position 4, France versus Spain. The script builds a cache from the first five tokens of the France prompt. Then it sends the last token of the Spain prompt, is, with that cache. The model answers Paris, with exactly the probabilities it gives the France prompt. As far as the model can tell, it was asked about France.

This is the kind of bug a runtime can have. It might reuse a cache because the earlier positions have the same count, without checking that they hold the same tokens. Or it might hand one conversation's cache to another. Either way, the model computes on text nobody sent in this conversation. The parameters are fine, and the model did exactly its job.

A cache is part of the input. Start each conversation with an empty cache, and reuse one only for the exact tokens it was built from.

Check

Two users chat with the same loaded model at the same time. What can they share, and what must each have alone?

Show the answer

They can share the parameters, which are only read. Each needs a separate cache, because a cache holds one conversation's earlier tokens.

Sort any array

Lesson 8

Every array the model learns, makes during a call, or keeps for a conversation fits one of the kinds in this table. The config is listed too, because it fixes the shapes. Three arrays sit outside the table: the token IDs, which are the input the tokenizer hands the model, and two small lists of 32 numbers that the model computes from the config when it loads, for marking positions.

Kind Example Shape Made by Lives Changes while running?
parameter layers.0.feed_forward.w1.weight (2560, 1024) training, then loaded from the weights file while the model is loaded never
activation block 5's output for the France prompt (1, 6, 1024) one call until the next layer has used it made fresh each call
cache block 2's keys (1, 8, n, 64) the loop, from activations one conversation grows one position per step
cache block 0's conv state (1, 1024, 3) the loop, from activations one conversation its three positions roll forward each step
config hidden_size one number, not an array the publisher ships with the model never

Three questions sort any array:

  1. What are its axes? Name each one before you index it.
  2. Who made it? Training made the parameters. One call made the activations. The loop made the cache. The publisher wrote the config.
  3. How long does it live? While the model is loaded, for one call, or for one conversation.

These questions also find the bugs in this chapter. The wrong-axis slice failed question 1. The stale cache failed question 3: it was used outside the conversation it belongs to. The double count needs one more check, for parameters: are two names the same array?

Check

A runtime holds an array of shape (1, 8, 412, 64) between calls. Which kind is it, and what does 412 tell you?

Show the answer

It is a cache: keys or values from an attention block. 412 is the number of positions the conversation has reached so far.

2.11Put it together#

You are hereThe whole machine

Every value in a running model is an array with named axes. Logits are (batch, position, vocabulary). Embeddings and block outputs are (batch, position, width). Name the axes before you index, and compare the shape you got with the shape you meant. The parameters are 132 learned arrays, 229,693,184 numbers, and a few config values fix every shape. A weight matrix is stored as (numbers out, numbers in). The output layer shares the embedding table, so count by storage, not by name. Activations are made for each call and grow with the batch and the positions. Running the model never changes a parameter. The cache keeps keys and values that grow by one position per step in the attention blocks, and a fixed three-position state in the conv blocks. The cache belongs to one conversation, and a stale one sends the model text from a different conversation.

The next chapter opens the weight matrices. It shows what multiplying a token's 1,024 numbers by a (2560, 1024) matrix computes, and why the shapes have to line up.
