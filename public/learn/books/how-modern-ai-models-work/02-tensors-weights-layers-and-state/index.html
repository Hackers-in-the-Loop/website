Learned, or made while it runs

Lesson 0

Chapter 1 ran a small open model, LiquidAI's LFM2.5-230M, on a laptop CPU. It ended on a question. Inside a running model, every number sits in an array. Which arrays did the model learn, and which exist only while it runs?

Some of each, plus one kind in between. A program you write already has all three. Some of its data is loaded at startup and never written. Some lives in a function's local variables, made during a call and gone after it. And some is state kept for one session. A running model has the same three lifetimes. Some arrays the model learned in training. It loads them from its file once and only reads them. Other arrays are made during one call to the model and dropped when the call is done. And while the model writes a reply, one kind of array is kept from each call to the next.

This chapter reads those arrays on the same model and sorts them. Reading comes first, because every array has sizes and each size counts something. Then come the learned arrays: their names, what their two sizes count, where those sizes come from, and how to count them. Then the arrays made for one call, and last the ones kept while a reply is written.

Sorting them pays off because mixing them up causes real bugs. We run three of them on this model, with real output. A slice of the model's output answers the wrong question and raises no error. A count of the learned numbers comes out 67 million too big. And a question about Spain gets the capital of France.

What you will be able to do#

  1. Read an array in a model as a list of lists, say what each of its sizes counts (prompts, tokens, numbers per token, scores per vocabulary entry), and say which list of scores is the next-token guess.
  2. Pick the slice you mean, every prompt's last token, and catch the wrong one from the size it returns, even when it prints believable tokens.
  3. Read a learned array's name as a path and its size as rows of a given length, trace every size to a few numbers in the config file, explain why the saved numbers only load at those sizes, and count the learned numbers once when one array has two names.
  4. Tell learned numbers from numbers made during a call: the made arrays grow with the input and are dropped, while the 132 learned arrays keep their size and are never written by running.
  5. Explain why a reply keeps a cache and what it keeps: the work for earlier tokens never changes, attention blocks keep numbers for every token so far, conv blocks keep the last three positions, and a cache belongs to one conversation.
  6. Sort any array a running model touches by what its sizes count, who made it and how long it lives, and name the chapter that opens each part.

Both lines run without an error, and both print real tokens. The wrong one even looks plausible. Its fourth entry is the model's guess after "The capital of", and the guess is France, at about 19 percent. A bug like this can slip past a quick look at the output.

Why can a model keep its earlier work? In this model, each token's numbers depend only on that token and the tokens before it. Attention lets a token look back at earlier tokens, never ahead. Block 2 is an attention block. Its keys are 1 prompt, 8 groups, 21 tokens so far, and 64 numbers per group. So for every token so far it keeps 512 numbers of keys, and as many of values. The token count grows by one each step, from 21 to 28. Block 0 is a conv block. Its conv state is 1 prompt, 1,024 numbers, and 3 positions. It never grows. Each step drops the oldest position and adds the newest.

These two arrays are a reason to say what each size counts instead of assuming where it sits. In the keys, the token level comes before the 64 numbers of each group. In the conv state, the 1,024 numbers come first and the 3 positions last.

Across the whole model, each of the six attention blocks keeps 2 × 8 × 64 = 1,024 numbers per token, 6,144 per token in all. The eight conv blocks keep 24,576 numbers in total, however long the reply runs. We calculated that at 10,000 tokens the cache would hold about 61 million numbers, about a quarter as many as the parameters.

The wrong cache

Lesson 11

The cache stands in for every earlier token. The model never sees those tokens again, only what the cache kept from them. So whatever is in the cache, the model takes as the conversation so far. In code, the danger is a cache stored under the wrong key. The server below keeps earlier words between requests. It keys them first by the prompt's word count, then by conversation:

Both prompts are 5 words long. Keyed by length, the Spain request finds France's stored words and answers Paris. Keyed by conversation, each request gets its own stored words, and the answers are Paris and Madrid. The function believes whatever words it is handed.

The real model does the same:

The two prompts are both six tokens long, counting the start token, and they differ only at position 4, France against Spain. The script builds a cache from the first five tokens of the France prompt. Then it sends the last token of the Spain prompt, is, with that cache. The model answers Paris, with exactly the probabilities it gives the France prompt, 95.22 percent for Paris. As far as the model can tell, it was asked about France.

A runtime that reuses a cache because the earlier tokens have the same count, without checking that they are the same tokens, makes this bug. So does one that hands one conversation's cache to another. The parameters are fine, and the model did exactly its job.

A cache is part of the input. Start each conversation with an empty cache, and reuse one only for the exact tokens it was built from.

Sort any array

Lesson 12

Three questions place any array a running model touches:

  1. What do its sizes count? Say it before you index the array.
  2. Who made it? Training made the parameters. One call made the activations. The loop made the cache from activations. The publisher wrote the config.
  3. How long does it live? As long as the model is loaded, for one call, or for one conversation.

parameter layers.0.feed_forward.w1.weight 2,560 rows of 1,024 training, then loaded from the file as long as the model is loaded no
activation block 5's output for the France prompt 1 prompt, 6 tokens, 1,024 numbers each one call until the next layer has used it, the call at most made fresh each call

Two kinds of array sit outside the table. The token IDs are the input the tokenizer hands the model. And when the model loads, it computes two small lists of 32 numbers from the config, which it uses to mark positions. They are not parameters, and training did not set them.

The questions also find this chapter's bugs. The wrong slice failed the first question, because its first size counted positions where it should have counted prompts. The stale cache failed the third, because it was used outside the conversation it lives for. The double count needs one more check for learned arrays: are two names the same array?

2.14Put it together#

You are hereThe whole machine

Every number in a running model sits in an array, a list of lists. Each level of nesting is an axis, and each size counts one thing, such as prompts, tokens or numbers per token. The scores hold one list per position, and only the last position's list is the next-token guess, so the slice you want is every prompt's last position. The wrong slice runs and prints real tokens, and only its size gives it away. The model's learned numbers sit in 132 named arrays. A name is a path to a block and a part, and a weight matrix's size is its rows (numbers out) by its row length (numbers in). A few numbers in the config file set every size, and the learned numbers only load at the sizes they were trained at. One table is saved under two names, so count arrays, not names. Every call makes activations that grow with the input and are dropped, while the parameters are only read. In this model, adding a token never changes the work done for earlier tokens, so a reply keeps that work in a cache and sends one new token per call. Attention blocks keep keys and values for every token so far, and conv blocks keep the last three positions. The cache stands in for the conversation, so it belongs to exactly one.

The next chapter opens the weight matrices. A token's 1,024 numbers go into w1, a grid the model learned, and 2,560 numbers come out. How does each row turn a token's 1,024 numbers into its one number?

Terms · 27 in this chapter

parameters
The model's learned numbers, also called weights. Training sets them. Running the model only reads them.
axis
One level of a nested array. The first index you write picks along the first axis, the next index along the second.
shape
The sizes of a nested array, from the outermost list in. Each size counts one thing, such as prompts, tokens, or numbers per token.
tensor
What libraries call an array of numbers, often nested: a list of lists of lists. Every number in a running model sits in one.
batch
Several independent prompts stacked into one array, so one call handles them all.
position
Where a token sits in the sequence: 0 for the first token, 1 for the next.
width
How many numbers describe one token inside the model: 1,024 here.
embedding
The list of 1,024 numbers the model looks up for a token ID: one row of a big learned table.
scores
The raw numbers the output layer gives every possible next token, also called logits.
vocabulary
Every token the model can score: 65,536 of them for this model.
block
One repeated stage that reworks every token's numbers. This model stacks 14 of them.
mixer
The part of a block where tokens share information with each other.
attention
A mixer that lets each token pull information from every earlier token, weighted by content.
conv
A mixer that blends each token with the two tokens just before it (short for convolution).
layer
A word with two meanings. In this model's code and config a layer is a block. People also use the word for one grid of learned numbers inside a block.
weight matrix
A grid of numbers the model learned in training. Each row makes one output number and is as long as the list it takes in.
feed-forward
The part of a block that reworks each token's numbers on its own, widening them and narrowing back.
config
The model's description file, config.json. Its numbers, like the width and the number of blocks, set the size of every learned array. It holds no learned numbers.
settings file
The file shipped with a model that sets default picking rules and the stop token (generation config).
state_dict
The dict from name to array that saving code writes out. An array shared by two parts appears once under each name.
activation
An array the model computes during one call, like a block's output. Made fresh each call, then dropped.
loop
Call the model, pick one token, append it to the input, and call again, until a stop token appears.
state
Data the model carries from one call to the next, like the cache.
cache
What the model keeps between steps of one reply, so earlier tokens are not recomputed. It belongs to one conversation.
keys and values
The numbers an attention block keeps for every token so far, so each new token can look back at them.
conv state
What a conv block keeps between calls: the numbers it blends, for the last three positions.
start token
A special token, ID 1, placed before your text to mark the start of a sequence.

  1. Lesson 0

    Learned, or made while it runs

    Every number in a running model sits in an array; some arrays the model learned and only reads, some are made during one call and dropped, and one kind is kept from call to call while a reply is written.

  2. Lesson 1

    An array of arrays

    An array in a model is a list of lists of lists; each level is an axis, and each size counts one thing, such as prompts, tokens, or numbers per token.

  3. Lesson 2

    A score for every token, at every position

    The scores hold one list per position, a score for every vocabulary entry, and each list guesses the token after its position; only the last position's list is the next-token guess.

  4. Lesson 3

    The wrong axis

    logits[-1] runs without an error and prints real tokens, but it takes every position of the last prompt instead of the last position of every prompt; its first size gives it away.

  5. Lesson 4

    A weight's name is a path

    The model's 229,693,184 learned numbers sit in 132 named arrays, and a name is a path, from block to part to weight; every block of a kind holds the same arrays, so the name is how you tell them apart.

  6. Lesson 5

    Rows out, row length in

    A grid is a list of lists: the number of rows is how many numbers come out, and each row's length is how many go in; a learned grid like this is a weight matrix, and w1's 2,560 rows of 1,024 take a token's 1,024 numbers and give 2,560.

  7. Lesson 6

    The config sets every size

    Code builds empty arrays at the sizes a short config file sets and the weights file fills them; the config holds no learned numbers, and the learned numbers only fit the sizes they were trained at.

  8. Lesson 7

    Count once

    A dict of names can list one array twice, so count arrays, not names: this model's saved listing names its shared table twice, 296,802,048 numbers instead of 229,693,184.

  9. Lesson 8

    Made for one call

    Every call makes new arrays, activations, that grow with the input and are dropped, while the 229,693,184 learned numbers keep their size and are only read.

  10. Lesson 9

    Redo or remember

    Adding a token never changes the work already done for earlier tokens, so a reply can keep that work, the cache, and send one new token per call: the same 64 tokens with 84 tokens sent instead of 3,360.

  11. Lesson 10

    What the cache keeps

    What a block keeps depends on how far back it looks: an attention block keeps keys and values for every token so far, growing one token per step, while a conv block keeps a fixed conv state of the last three positions.

  12. Lesson 11

    The wrong cache

    A cache built from the France prompt, sent with the Spain prompt's last token, makes the model answer Paris with France's exact probabilities: a cache belongs to one conversation.

  13. Lesson 12

    Sort any array

    Three questions sort every array a running model touches (what its sizes count, who made it, how long it lives), and each part opens in a later chapter.
